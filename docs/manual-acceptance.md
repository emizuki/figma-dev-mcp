# Manual acceptance

Spec §19.6 checks against a representative Figma file in Dev Mode. This file is the checklist and the record. It does not embed node text, design names, or image payloads.

The automated suite in [testing.md](testing.md) does **not** replace this gate. If a representative Figma file or an interactive Figma session is unavailable, mark the gate **pending**. Do not claim the MVP complete and do not fabricate results.

All nine §19.6 scenarios were run against live Dev Mode sessions on 2026-08-19, driven through a follower `figma-dev-mcp` stdio process speaking MCP to the leader broker. Over 100 live tool calls across ten phases; every one of the 14 read tools was exercised, and each tool's optional parameters were exercised separately rather than left at their defaults.

Two of the nine required a human observer and are recorded on their word: "Document unchanged" and "No local export".

The gate being met is a statement about the nine scenarios, not a claim that no defects exist. Seven defects were found during this run, an eighth was found while fixing them, and all eight are listed below with their outcomes; each scenario's own expectation was still satisfied at the time. One supplementary check beyond the nine — "Text style units" — remains open because its `auto` branch has never been observed against live data.

## Defects observed during the 2026-08-19 run

All seven were fixed on 2026-08-20 and re-measured against a live session. **The list is kept rather than deleted**: a defect list that silently shrinks loses the record that these existed and how they were found. Each entry now carries its original finding, then its outcome.

Every "after" number below was taken on the same page as its "before" number, so the two are comparable.

1. `get_variables` ignores its `selector` and returns only variables local to the document. On the anchor frame, `get_design_context` reported 26 variable references spanning 11 distinct ids, all of them in the library id form (`VariableID:<hash>/<number>`); `get_variables` for the same scope returned 2 variables, both in the local id form, and the two sets did not intersect at all. The same 2 variables came back for a single text node, a frame, a whole page, a `pageIds` selector, and an empty selection. Definitions, modes, and `codeSyntax` for the variables actually in use are therefore unreachable. Their names are still reachable through `variableReferences[].name`. Scoping by `connectionId` is unaffected — a second document returned 0. **Fixed 2026-08-20.** `get_variables` now derives its set from the scope: it collects variable ids out of `boundVariables` and resolves each through `figma.variables.getVariableByIdAsync`, so library variables appear. Re-measured on the same frame: the 11 bound ids went from **0 of 11** returned to **11 of 11**, inside 52 variables across 16 collections, **all 52 carrying values** and none empty. Different scopes now return different sets (52 for the frame, 76 for the page), proving `selector` is live. An open question from the fix — whether library *collections* resolve by id at all — was settled by this run: all 16 came back with real names, 0 with an empty name and 0 with zero modes, so the salvage path built for the opposite case never fires on real data. Cost: the payload grew from 1,788 B to 23,608 B on the frame, because the tool returns whole collections rather than only the bound variables.
2. `get_dev_mode_data`, `get_reactions`, and `get_motion` emit one record per visited node whether or not that node has anything to report. Measured on one page: `get_dev_mode_data` 563 items / 175,226 B of which **1** carried content; `get_reactions` 2,000 items / 356,668 B of which **11** carried content; `get_motion` 563 items / 237,212 B with zero animations and 563 timelines all reporting the same duration. `get_reactions` exhausted the node budget doing this and stopped with `{"reason":"nodeLimit","visitedNodes":2001}`, so any reaction past that point is absent without the caller being told which nodes went unvisited. **Fixed 2026-08-20**, and the data loss was larger than the original entry could show. Each tool now emits a record only for nodes with something to report, and each response carries a `visitedNodes` count so a caller can still tell "scanned and found nothing" from "never reached". Re-measured on the same page: `get_dev_mode_data` **563 items / 175,226 B → 1 item / 343 B**, visitedNodes 565. `get_motion` **563 items / 237,212 B → 0 items / 145 B**, visitedNodes 565, and with no `UNSUPPORTED_NODE` entries at all. `get_reactions` **2,000 items / 356,668 B → 64 items / 12,127 B**, and it no longer truncates: it now walks **9,204** nodes instead of stopping at 2,001, and returns **64** reactions where it previously returned 11. Fifty-three real reactions were being lost.
3. `get_design_context` misreports why it truncated. Reading a whole page at `detail: "full"`, `depth: 6` returned exactly 2,000 nodes — the node cap — but reported `{"reason":"depthLimit","appliedDepth":6}` and no `visitedNodes`. Corroborated within the same session: `get_reactions` on that same page reported `nodeLimit` at `visitedNodes: 2001`, so the page holds more than 2,000 reachable nodes. The same read at `depth: 5` returned 1,119 nodes and at `depth: 3` returned 295. A caller told `depthLimit` would reduce depth, which loses more data rather than less. **Fixed 2026-08-20.** Truncation precedence now lets a global budget outrank an earlier depth cut, while each node's own `childrenTruncation` still reports `depthLimit` where that is the local truth. The same read now reports `{"reason":"nodeLimit","visitedNodes":2001}`.
4. `get_screenshot` with `svgOutlineText: false` fails: `UNSAFE_SVG` on a frame, `INTERNAL_ERROR` on a single text node. Two different failures from one flag suggests two distinct paths, not one policy. **Fixed 2026-08-20, and the original diagnosis was wrong.** This entry attributed the failure to an embedded font data URL. The live re-run shows the flag now succeeds and returns **98 `<text>` elements with no `@font-face` present at all**, so the font allowlist was not what was blocking it. The actual cause was an attribute classifier that treated any `alpha…:` value as a URI scheme, so an `id` derived from a layer name containing a colon was rejected as an unsafe attribute. The `INTERNAL_ERROR` half of this entry was a separate defect entirely — see item 8 below, which did not exist when this list was written.
5. `get_screenshot` with `svgIdAttribute: true` fails with `UNSAFE_SVG`. Adding `id` attributes should not make an export unsafe. Isolated one flag at a time on the same node: the default succeeded, `svgSimplifyStroke: false` succeeded, and these two did not. **Fixed 2026-08-20**, same root cause as item 4. The flag now succeeds, returning **611 `id` attributes** with `safe: true` and no rejection. The instrument that made this diagnosable — a reason discriminator on the rejection — was built first precisely because the trigger could not be identified from outside.
6. `capabilities.annotations` is always false. `plugin/src/read/common.ts:79` probes `"annotations" in figma.currentPage`, but `annotations` belongs to `AnnotationsMixin`, which `PageNode` does not extend. Contradicted live in the same session: `get_metadata` reported `annotations: false` while `get_dev_mode_data` returned a real annotation on a scene node. A client that trusts the capability would skip a tool that works. **Fixed 2026-08-20.** The probe now reads the annotations API rather than the page. Confirmed live in a session where an annotation exists: `capabilities.annotations` reports `true`.
7. `get_components` returns instance-to-component ids it cannot resolve. At page scope it returned 1,196 instances and **0** components, because it collects only COMPONENT and COMPONENT_SET nodes inside the selector's own subtree (`plugin/src/read/components.ts:242`) and the definitions live elsewhere. `search_nodes` confirmed no component definition exists on that page. A workaround was verified: `get_nodes` on the reported `componentId` resolves it, including across pages, returning the component's name and its `data.component`. Lowest severity of the seven for that reason. **Fixed 2026-08-20.** Component ids reported by in-scope instances are now resolved by id even when the definition lives on another page or in a library. Re-measured at page scope: **0 components → 66**, against 1,196 instances, covering **66 of 66** distinct `componentId` values.

8. **Found on 2026-08-19 while isolating items 4 and 5, after this list was first written.** `get_screenshot` at `format: "svg"` returned `INTERNAL_ERROR` for some nodes, including at default settings, which initially looked like a flag defect and was not: a different nested node exported cleanly, and the failing node exported as PNG at 1×1 pixels and 149 decoded bytes. **Fixed 2026-08-20, and the first fix was wrong in an instructive way.** The first attempt keyed on non-positive width or height. The live re-run shows that rule was inverted on real data: the two nodes that genuinely render nothing measure **20×20** and **50×24** — both positive, so a geometric rule misses both — while a LINE node measures **20 high by 0 wide** and exports perfectly well, returning a 1×20 raster. A geometric rule would therefore have scored 0 of 2 on real failures and 1 of 1 on false ones. The shipped rule instead asks whether the node reports any render bounds at all, guarded by a parent-visibility walk so that a switched-off ancestor is not mistaken for an empty node. Both failing nodes now return `EMPTY_NODE_BOUNDS`; the LINE still exports, in SVG and in raster.

A design change also landed alongside these fixes, at the operator's decision: **SVG safety now declares rather than blocks.** `get_screenshot` always returns the SVG source, with a required `safe` boolean and, when unsafe, a reason naming the rule and the offending element or attribute. Nothing is withheld for safety. The trade was made deliberately: withholding destroyed information the caller could use, and the consumer here is an agent reading a JSON string over a local read-only server rather than a browser rendering untrusted input. One limitation is stated rather than fixed, also by decision: the `image/svg+xml` content block carries no verdict, so a client that auto-previews it renders an unsafe SVG unlabelled. The verdict is present in structured content beside it.

Two further observations, neither a defect:

- `get_styles` with `source: "local"` also ignores the `selector`, returning a byte-identical 47-style, 37,882 B payload for a text node, a frame, a page, and an empty selection. Unlike item 1 this matches the tool's stated contract — "local styles **and** styles referenced by a bounded scope" — but the schema gives no signal that `selector` is inert for that half, and the `both` default mixes 47 document-wide entries with the few in scope. `source: "referenced"` scopes correctly: 1 style for a text node, 9 for a frame.
- The `byteLimit` truncation branch did not fire in any read attempted, including a 1,918,642-byte payload. `depth` is capped at 6 by the schema, so it may not be reachable in practice.

## Second document, 2026-08-20

Every measurement before this date came from one design file. That is a real limit on what any of it proves, and this project has already been bitten twice by a rule that looked right and was backwards until measured. A second document was read at the same build to test that: a publicly published design-system kit, picked for being variable-heavy and structurally unlike the first — 33 pages against 13, and a different authoring style throughout.

**It corrected a figure rather than confirming it, which is the point of running it.** Cost per variable had been derived from the first document at 454 and 460 bytes. The second reports 1,470 bytes at page scope and 1,662 across twelve pages, because its variables carry far more modes — 1,897 mode values across 160 variables. Headroom against the 8 MiB response cap is therefore roughly **5,000 variables, not the ~18,400 the first document implied**. Still comfortable for a real design system, but the single-document estimate was optimistic by a factor of 3.7.

**The SVG classifier flagged something for the first time on real data, and it was right.** Across nine exports from the first document nothing was ever flagged. Here, two of three successful exports came back unsafe, both `{"kind":"unsafeAttribute","name":"href"}`. The values are genuine external `http://` links, which the kit's documentation pages carry as hyperlinks and Figma exports as anchor elements. That is exactly what the rule exists to catch. The same exports embed a raster image as a data URL over 448,000 characters long, and that was correctly **accepted** — the classifier distinguishes an embedded payload that fetches nothing from a reference that reaches the network. Under declare-not-block the caller still received the full source alongside the verdict.

**Two boundary behaviours were reached that the first document never hit.** A frame of roughly 2,028 by 4,328 units produced an SVG past the 4 MiB export cap and returned a per-asset `LIMIT_EXCEEDED`. And `get_variables` across twelve pages truncated at `{"reason":"nodeLimit","visitedNodes":10000}` — the tree-walk budget, not the emission budget — so a very wide scope returns a partial variable set with the truncation stated rather than silently short.

Nothing regressed. `get_metadata`, `search_nodes`, `get_nodes`, `get_design_context` and `get_variables` all behaved as on the first document, and a truncation reported as `depthLimit` on a genuinely shallow page was correct rather than the misreport an earlier defect produced.

## How to run when a session is available

1. Follow [setup.md](setup.md): `cargo build --release`, import `plugin/manifest.json` as a development plugin in Dev Mode, configure the MCP client over stdio, start the plugin in each file.
2. Fill the record table (date, Figma desktop version from Figma → About, SHA-256 of the built `plugin/dist/code.js`, `figma-dev-mcp --version`).
3. Check each box only after observing the expected result. Do not paste design content into this file.
4. Use two genuinely different documents for the multi-connection checks. The same document opened twice yields two `connectionId` values but one file name, which does not satisfy the first scenario and makes any cross-document isolation probe vacuous — a node id from one session resolves in the other because they are one document.
5. Free `127.0.0.1:3056` and `127.0.0.1:3057` before running the Rust suite afterwards. A broker left holding them fails `crates/figma-dev-mcp/tests/stdio_eras.rs`, which reads as a code defect and is not one.
